# PostgreSQL Upgrade Brief Generator 작업 계획서

## 1. 문서 목적

이 문서는 PostgreSQL 공식 릴리스 노트를 기반으로 AS-IS/TO-BE 버전 간 변경사항을 수집·구조화·요약하고, 고객 전달용 HTML/DOCX/PDF 문서를 생성하는 시스템의 기준 계획이다.

실제 수행 결과는 `docs/WORK_LOG.md`에 같은 계획 ID로 기록한다. 계획과 실제가 다르면 작업 기록에 차이와 사유를 남기고, 승인 없이 완료로 처리하지 않는다.

## 2. 운영 원칙

1. 중요한 작업 전에 목적, 변경 대상, 검증 방법을 사용자에게 알린다.
2. 작업 후 실제 결과와 증거를 작업 기록에 남긴다.
3. 공식 PostgreSQL 문서를 단일 기준 원천으로 사용한다.
4. 수집한 원문 HTML과 응답 메타데이터는 불변 스냅샷으로 보관하며 파싱·분류·요약·사람 수정으로 덮어쓰지 않는다.
5. 공식 원문이 변경되면 기존 스냅샷을 수정하지 않고 새 해시의 스냅샷을 추가한다.
6. 구조화 항목, 규칙 분류, AI 요약, 사람 수정본과 최종 보고서는 원문과 분리해 저장하고 원본 스냅샷 ID를 참조한다.
7. AI 결과는 초안이며 입력 원문으로 뒷받침되지 않는 문장을 만들 수 없다.
8. 사람은 수천 개 원문을 항목별 승인하지 않고, 자동 생성된 최종 요약 초안을 검토·수정·확정한다.
9. 비밀정보, 고객정보, 개인키, 로컬 모델 파일은 Git에 저장하지 않는다.
10. Git 커밋과 GitHub push 전에는 변경 범위와 검증 결과를 먼저 알린다.
11. 서버 파일을 수동 편집해야 할 때는 `vi`를 기준으로 안내한다.

## 4. 범위

### 4.1 MVP 포함 범위

- PostgreSQL 공식 릴리스 목록과 릴리스 노트 수집
- 원문 HTML, 텍스트, 해시, URL, 수집시각 보관
- 메이저/마이너/베타/RC 버전 구분
- 변경 항목 구조화 및 분류
- AS-IS/TO-BE 범위 계산
- AI 기반 한국어 요약 초안
- 자동 주제 묶음, 중복 통합과 중요도 선별
- 원문 근거가 연결된 고객용·DBA용 AI 요약 초안
- 완성된 보고서 초안의 검토·수정·확정 이력
- 고객용 요약, 기술 상세 보고서
- HTML/일반 텍스트/Markdown 복사
- DOCX/PDF 다운로드
- 정기 신규 릴리스 감지
- 백업, 복구, 로그, 상태 점검

### 4.2 MVP 제외 범위

- 고객 DB에 직접 접속한 호환성 진단
- `pg_upgrade` 자동 실행
- 확장 모듈과 드라이버의 호환성 보장
- 다운타임 및 성능 개선 수치 보장
- 고객 메일 자동 발송
- 인터넷 공개 회원가입
- GPU 없는 VM에서 대형 로컬 모델 운영

## 5. 목표 구조

```text
PostgreSQL 공식 문서
        ↓
수집기 → 불변 원문 스냅샷 → 구조화 변경 항목
                                  ↓
                    범위 계산·주제 묶음·중복 통합
                                  ↓
                    OmniRoute를 통한 AI 요약 초안
                                  ↓
                  고객용·DBA용 보고서 초안 자동 생성
                                  ↓
                    사람의 최종 검토·수정·확정
                                  ↓
                       HTML / DOCX / PDF
```

원문과 가공 데이터의 저장 경계:

```text
source_snapshot   원문 HTML·해시·URL·수집시각 (불변)
change_item       원문에서 추출한 구조화 항목 (원문 참조)
summary_group     주제·변경유형별 묶음과 포함 원문 ID
ai_summary        모델·프롬프트·근거 원문 ID·생성 결과
report_draft      고객용/DBA용 자동 생성 초안
report_revision   사람이 수정한 버전과 변경 이력
report            최종 확정본과 출력 파일
```

VM 내부 서비스는 다음과 같이 분리한다.

```text
proxy       HTTPS와 접근 제어
web         Django 웹과 API
systemd     Django 관리 명령을 이용한 정기 수집
db          애플리케이션 PostgreSQL
omniroute   AI 공급자 라우팅
ollama      로컬 ornith:9b 후보
```

## 6. AI 라우팅 정책

### 6.1 우선순위

1. 로컬 Ollama `ornith:9b`
2. Google API
3. Grok(xAI) API
4. Mistral API

이 순서는 OmniRoute에서 고정한다. 자동으로 임의의 모델을 선택하지 않는다.

### 6.2 로컬 모델 채택 기준

VM에서 실제 벤치마크한 뒤 다음 조건을 모두 충족해야 기본 경로로 채택한다.

- JSON Schema 유효 응답률 100%
- 테스트 원문에 없는 사실을 생성하지 않음
- 짧은 변경 항목 응답 20초 이내
- 중간 길이 항목 응답 60초 이내
- 실행 중 VM 가용 메모리 4GB 이상 유지
- 웹과 DB 상태 점검에 장애가 없음
- 연속 20건 처리 중 프로세스 오류가 없음

기준을 충족하지 못하면 Ollama를 제거하지 않고 다음 중 하나로 제한한다.

- 백그라운드 저우선순위 초안 생성
- 짧은 항목만 처리
- 제한시간 초과 시 Google로 전환

### 6.3 외부 공급자 활성화 기준

- 공식 API 방식 사용
- 사용 가능한 모델을 연결 시점에 확인
- 무료 한도와 상업적 이용조건 확인
- 유료 자동 전환을 공급자 설정에서 차단
- 애플리케이션 일/월 요청 한도 설정
- API 키는 VM 비밀 설정에만 저장
- 공급자별 실제 JSON, 한국어, 지연시간 시험 통과

### 6.4 AI 공통 안전장치

- 원문 스냅샷은 AI 입력 처리 전후에 절대 갱신하지 않음
- 범위 전체를 한 번에 넣지 않고 주제별 묶음으로 분할 요청
- JSON Schema 강제
- 낮은 temperature
- 모든 요약 문장에 근거 source item ID 필수
- 프롬프트 버전과 모델명 기록
- 추가·변경·제거·폐기·버그 수정·보안·호환성 범주를 구분
- 중복 통합 시 포함된 모든 source item ID 보존
- 근거 없는 숫자·지원 여부·성능 효과 생성 금지
- AI 초안과 사람 수정본을 별도 버전으로 보존
- AI 실패가 원문 수집과 기존 보고서 조회를 막지 않음

## 7. 데이터 기준

주요 엔터티는 다음과 같다.

- `release`: 버전, 종류, 날짜, 지원상태
- `source_snapshot`: URL, 원문, 해시, 수집시각
- `change_item`: 섹션, 원문, 변경유형, 분야
- `change_relation`: 도입/변경/폐기/제거 관계
- `summary_group`: 주제, 변경유형, 중요도, 포함 원문 ID
- `ai_summary`: 모델, 프롬프트 버전, JSON 결과, 근거 원문 ID
- `report_draft`: AS-IS, TO-BE, 고객/DBA 수준, 자동 생성 초안
- `report_revision`: 수정자, 수정 내용, 수정시각과 이전 버전
- `report`: 최종 확정상태, 고객정보, 생성 파일
- `job_run`: 수집·요약·문서 작업 실행 결과
- `audit_log`: 중요 관리 행위

## 8. 단계별 계획과 완료 조건

구현 우선순위:

```text
P00~P02 기반 환경
→ P04 애플리케이션·DB 골격
→ P05 공식 문서 수집과 원문 스냅샷
→ P06 버전 비교 엔진
→ P03 로컬 모델 재검증
→ P07 주제별 자동 요약·OmniRoute
→ P08 최종 보고서 초안 검토 화면
→ P09 확정 보고서 출력
→ P10 운영·복구 보완
→ P11 최종 검증과 출시
```

- 공식 원문 수집과 범위 비교 기반이 완료됐으므로 P03과 P07을 지금 진행한다.
- AI 없이도 공식 원문 수집, 보존, 범위 비교와 기존 데이터 조회는 정상 동작해야 한다.
- AI 장애나 미구성 상태가 원문 수집과 기존 데이터 조회를 막아서는 안 된다.
- P08과 P09의 기존 개별 항목 승인 중심 구현은 보조 기능으로 내리고 보고서 초안 중심으로 재작업한다.

### P00 문서 및 Git 기준선

작업:

- 계획서와 작업 기록 생성
- GitHub SSH 원격 연결
- 비밀정보 제외 규칙 생성
- 커밋 및 push 절차 확정

완료 조건:

- 계획 ID와 작업 기록 ID가 대응됨
- 원격 저장소 접근 확인
- `.env`, 키, 모델, DB, 생성문서가 추적 제외됨

### P01 VM 안정화

작업:

- Chrony 미동기화 원인 해결
- OS 보안 업데이트와 재부팅
- SSH 공개키 재접속 검증
- 방화벽과 공개 포트 정책 적용
- 서버 애플리케이션 디렉터리 확정

완료 조건:

- `chronyc tracking`이 동기화 상태
- 업데이트 후 SSH 접속 정상
- 외부 공개 포트는 승인된 포트만 존재

### P02 컨테이너 실행 기반

작업:

- Docker Engine과 Compose 설치
- 프로젝트 네트워크와 볼륨 정의
- 로그 크기 제한
- 컨테이너 재시작 정책
- 상태 점검과 자원 제한

완료 조건:

- VM 재부팅 후 필수 컨테이너 자동 시작
- 로그 무제한 증가 방지
- 내부 서비스 포트가 외부에 노출되지 않음

### P03 로컬 Ollama 벤치마크

진행 시점: P05 원문 수집과 P06 범위 비교가 완료된 현재 재개.

작업:

- 시험용 Ollama와 `ornith:9b` 준비
- 짧은/중간/긴 PostgreSQL 항목 테스트
- JSON 강제, thinking 비활성화 테스트
- 처리시간, 토큰속도, 메모리, CPU 기록
- 연속 처리 안정성 시험

완료 조건:

- 6.2의 채택 기준 결과가 작업 기록에 수치로 남음
- 채택/제한/탈락 결론과 사유가 기록됨

### P04 애플리케이션 골격

작업:

- Django와 PostgreSQL 구성
- 수집용 Django 관리 명령과 systemd timer 구성
- 관리자 인증과 권한
- DB 마이그레이션
- 상태 점검 URL
- 기본 감사 로그

완료 조건:

- 로그인과 권한 분리 정상
- DB 장애를 상태 점검에서 감지
- 재배포 후 데이터 유지

### P05 공식 문서 수집기

작업:

- 릴리스 인덱스 수집
- 원문 스냅샷과 해시
- 릴리스 노트 계층 파싱
- 중복 방지와 변경 감지
- 실패 항목 격리
- 원문과 가공 데이터의 물리적·논리적 저장 분리
- 원문 스냅샷 수정 방지와 새 해시 추가 저장

완료 조건:

- 재수집 시 중복 없음
- 모든 항목에 공식 URL과 원문 존재
- 파싱 실패가 별도 오류로 노출됨
- 원문 변경 시 이전 스냅샷 유지
- 파싱·분류·AI 요약·사람 수정 전후에 원문 해시가 변하지 않음
- 원문 수정 API와 관리자 수정 경로가 존재하지 않음

### P06 버전 비교 엔진

작업:

- PostgreSQL 10 이전/이후 버전 규칙
- 시작 패치 이후와 목표 패치까지 범위 계산
- 메이저 기능과 마이너 수정 분리
- 지원상태와 EOL 표시
- 변경 관계 후보 관리
- 변경유형·기능영역·주제별 자동 묶음
- 동일하거나 연속된 마이너 수정의 중복 통합 후보 생성
- 고객 영향도와 DBA 중요도 후보 계산

완료 조건:

- `9.2.10 → 18.4` 포함 범위 검증
- 역방향과 잘못된 버전 차단
- 베타/RC 기본 제외
- 각 묶음에서 포함된 모든 공식 원문 항목으로 역추적 가능
- 묶음 생성이 원문과 구조화 원문 텍스트를 변경하지 않음

### P07 AI 및 OmniRoute

진행 시점: 수집·파싱·범위 비교가 완료됐으므로 P03 검증과 함께 진행.

작업:

- LLM 공급자 공통 인터페이스
- Ollama → Google → Grok → Mistral 경로
- 제한시간, 재시도, 회로차단
- JSON 검증과 근거 검증
- 비용과 호출량 기록
- 주제별 묶음을 추가·변경·제거·폐기·버그 수정·보안·호환성으로 요약
- 고객용 핵심 요약과 DBA용 기술 상세 초안을 각각 생성
- 사소한 반복 수정은 통합하되 포함 원문 ID 전체 보존
- 요약 결과를 조합해 2~4페이지 수준의 보고서 초안 자동 생성

완료 조건:

- 각 활성 공급자 연결 시험 통과
- 제한시간 초과 시 다음 경로 동작
- 모든 경로 실패 시 작업이 실패 상태로 보존
- 잘못된 JSON이 승인 데이터로 저장되지 않음
- 모든 요약 문장이 하나 이상의 공식 원문 ID로 역추적 가능
- 대표 구간에서 수천 개 원문이 사람이 검토할 소수의 요약 문단으로 축약됨
- AI 실행 전후 원문 스냅샷 해시가 동일함

### P08 검수 및 고객 화면

작업:

- AS-IS/TO-BE 선택
- 고객용/DBA용 자동 생성 보고서 초안을 기본 화면으로 표시
- 추가·변경·제거·폐기·버그 수정·보안·호환성별 요약 표시
- 요약 문단의 근거 원문 펼쳐보기
- 보고서 전체 또는 요약 문단 단위 수정과 재생성
- 최종 확정 및 수정 이력
- 기존 원문 항목별 승인·반려는 예외 조사용 보조 화면으로 유지

완료 조건:

- 사용자가 원문 수천 개를 개별 승인하지 않고 완성된 초안부터 검토함
- 모든 요약 문단에서 근거 공식 원문으로 이동 가능
- 수정 전 AI 초안과 수정 후 문안이 모두 보존됨
- 권한 있는 사용자만 보고서를 최종 확정함

### P09 출력 문서

작업:

- HTML, 텍스트, Markdown 복사
- DOCX와 PDF 생성
- 한글 글꼴과 표 레이아웃
- 고객명, 프로젝트명, 로고 결합
- 최종 확정된 보고서 revision을 출력 원천으로 사용

완료 조건:

- HTTPS에서 클립보드 복사 정상
- Word에서 DOCX 정상 열림
- PDF 한글과 표가 깨지지 않음
- 화면, DOCX, PDF의 핵심 내용이 동일
- 개별 원문 목록이 아니라 자동 요약된 최종 결과가 기본 출력됨
- 각 요약에 공식 근거 링크 또는 부록이 포함됨

### P10 운영과 복구

작업:

- DB와 파일 외부 백업
- 복구 자동화와 복구 시험

- 공식 사이트와 AI 장애 중 기존 보고서 조회 가능
- 디스크 70% 이상 경고
- VM 재부팅 후 서비스 자동 복구

### P11 시범 검증과 출시

검증 경로:

- 14.x → 18.x
- 인접 메이저 버전
- 동일 메이저 내 마이너 버전

완료 조건:

- 자동 생성된 대표 보고서의 모든 요약 문장을 공식 원문과 대조
- 발견된 사실 오류 수정
- 알려진 한계가 보고서에 표시됨
- 사용자가 수천 개 원문을 개별 검토하지 않고 최종 초안만 수정해 문서를 완성함
- 출시 체크리스트 완료

## 9. Git 작업 방식

1. 로컬 작업 폴더가 소스 기준이다.
2. 기능별 작은 커밋을 사용한다.
3. 커밋 전 테스트와 변경 요약을 확인한다.
4. 사용자에게 알린 뒤 `main`에 push한다.
5. VM 배포는 Git 기준 커밋을 사용한다.
6. VM에서 직접 수정하지 않는다. 긴급 수정도 로컬에 역반영한다.

권장 커밋 형식:

```text
docs: add project plan and work log
infra: add compose runtime
feat: collect PostgreSQL release notes
test: cover pre-10 version ordering
fix: preserve failed parser items
```
