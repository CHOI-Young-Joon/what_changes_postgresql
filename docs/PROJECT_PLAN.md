# PostgreSQL Upgrade Brief Generator 작업 계획서

## 1. 문서 목적

이 문서는 PostgreSQL 공식 릴리스 노트를 기반으로 AS-IS/TO-BE 버전 간 변경사항을 수집·구조화·요약하고, 고객 전달용 HTML/DOCX/PDF 문서를 생성하는 시스템의 기준 계획이다.

실제 수행 결과는 `docs/WORK_LOG.md`에 같은 계획 ID로 기록한다. 계획과 실제가 다르면 작업 기록에 차이와 사유를 남기고, 승인 없이 완료로 처리하지 않는다.

## 2. 운영 원칙

1. 중요한 작업 전에 목적, 변경 대상, 검증 방법을 사용자에게 알린다.
2. 작업 후 실제 결과와 증거를 작업 기록에 남긴다.
3. 공식 PostgreSQL 문서를 단일 기준 원천으로 사용한다.
4. AI 결과는 초안이며 사람의 승인 전에는 고객 문서에 포함하지 않는다.
5. 입력 원문으로 뒷받침되지 않는 AI 문장은 승인할 수 없다.
6. 비밀정보, 고객정보, 개인키, 로컬 모델 파일은 Git에 저장하지 않는다.
7. Git 커밋과 GitHub push 전에는 변경 범위와 검증 결과를 먼저 알린다.
8. 서버 파일을 수동 편집해야 할 때는 `vi`를 기준으로 안내한다.

## 4. 범위

### 4.1 MVP 포함 범위

- PostgreSQL 공식 릴리스 목록과 릴리스 노트 수집
- 원문 HTML, 텍스트, 해시, URL, 수집시각 보관
- 메이저/마이너/베타/RC 버전 구분
- 변경 항목 구조화 및 분류
- AS-IS/TO-BE 범위 계산
- AI 기반 한국어 요약 초안
- 원문과 요약을 나란히 보는 관리자 검수
- 승인/반려/수정 이력
- 고객용 요약, 기술 상세 보고서
- HTML/일반 텍스트/Markdown 복사
- DOCX/PDF 다운로드
- 정기 신규 릴리스 감지
- 백업, 복구, 로그, 상태 점검

### 4.2 MVP 제외 범위

- 고객 DB에 직접 접속한 호환성 진단
- `pg_upgrade` 자동 실행
- 확장 모듈과 드라이버의 호환성 보장
- 다운타임 및 성능 개선 수치 보장
- 고객 메일 자동 발송
- 인터넷 공개 회원가입
- GPU 없는 VM에서 대형 로컬 모델 운영

## 5. 목표 구조

```text
PostgreSQL 공식 문서
        ↓
수집기 → 원문 스냅샷 → 구조화 변경 항목
                              ↓
                       AI 요약 단계(후순위)
                              ↓
                  OmniRoute 우선순위 라우팅
                              ↓
                       사람 검수 및 승인
                              ↓
              웹 비교 / HTML / DOCX / PDF
```

VM 내부 서비스는 다음과 같이 분리한다.

```text
proxy       HTTPS와 접근 제어
web         Django 웹과 API
systemd     Django 관리 명령을 이용한 정기 수집
db          애플리케이션 PostgreSQL
omniroute   AI 공급자 라우팅
ollama      로컬 ornith:9b 후보
```

## 6. AI 라우팅 정책

### 6.1 우선순위

1. 로컬 Ollama `ornith:9b`
2. Google API
3. Grok(xAI) API
4. Mistral API

이 순서는 OmniRoute에서 고정한다. 자동으로 임의의 모델을 선택하지 않는다.

### 6.2 로컬 모델 채택 기준

VM에서 실제 벤치마크한 뒤 다음 조건을 모두 충족해야 기본 경로로 채택한다.

- JSON Schema 유효 응답률 100%
- 테스트 원문에 없는 사실을 생성하지 않음
- 짧은 변경 항목 응답 20초 이내
- 중간 길이 항목 응답 60초 이내
- 실행 중 VM 가용 메모리 4GB 이상 유지
- 웹과 DB 상태 점검에 장애가 없음
- 연속 20건 처리 중 프로세스 오류가 없음

기준을 충족하지 못하면 Ollama를 제거하지 않고 다음 중 하나로 제한한다.

- 백그라운드 저우선순위 초안 생성
- 짧은 항목만 처리
- 제한시간 초과 시 Google로 전환

### 6.3 외부 공급자 활성화 기준

- 공식 API 방식 사용
- 사용 가능한 모델을 연결 시점에 확인
- 무료 한도와 상업적 이용조건 확인
- 유료 자동 전환을 공급자 설정에서 차단
- 애플리케이션 일/월 요청 한도 설정
- API 키는 VM 비밀 설정에만 저장
- 공급자별 실제 JSON, 한국어, 지연시간 시험 통과

### 6.4 AI 공통 안전장치

- 입력 변경 항목 단위로 요청
- JSON Schema 강제
- 낮은 temperature
- source item ID 필수
- 프롬프트 버전과 모델명 기록
- 압축 기능 비활성화
- 승인 전 고객 문서 포함 금지
- AI 실패가 원문 수집과 기존 보고서 조회를 막지 않음

## 7. 데이터 기준

주요 엔터티는 다음과 같다.

- `release`: 버전, 종류, 날짜, 지원상태
- `source_snapshot`: URL, 원문, 해시, 수집시각
- `change_item`: 섹션, 원문, 변경유형, 분야
- `change_relation`: 도입/변경/폐기/제거 관계
- `ai_summary`: 모델, 프롬프트 버전, JSON 결과
- `review`: 승인상태, 검수자, 수정 및 사유
- `report`: AS-IS, TO-BE, 고객정보, 생성 파일
- `job_run`: 수집·요약·문서 작업 실행 결과
- `audit_log`: 중요 관리 행위

## 8. 단계별 계획과 완료 조건

구현 우선순위:

```text
P00~P02 기반 환경
→ P04 애플리케이션·DB 골격
→ P05 공식 문서 수집과 원문 스냅샷
→ P06 버전 비교 엔진
→ P08 원문 중심 검수·조회 화면
→ P09 출력 문서
→ P10 운영·복구
→ P03/P07 AI 요약·OmniRoute
→ P11 최종 검증과 출시
```

- AI 없이도 공식 원문 수집, 버전 비교, 조회와 문서 출력이 정상 동작해야 한다.
- P03과 P07은 데이터 수집·비교·출력 기반이 완성된 뒤 진행한다.
- AI 장애나 미구성 상태가 원문 수집과 기존 데이터 조회를 막아서는 안 된다.

### P00 문서 및 Git 기준선

작업:

- 계획서와 작업 기록 생성
- GitHub SSH 원격 연결
- 비밀정보 제외 규칙 생성
- 커밋 및 push 절차 확정

완료 조건:

- 계획 ID와 작업 기록 ID가 대응됨
- 원격 저장소 접근 확인
- `.env`, 키, 모델, DB, 생성문서가 추적 제외됨

### P01 VM 안정화

작업:

- Chrony 미동기화 원인 해결
- OS 보안 업데이트와 재부팅
- SSH 공개키 재접속 검증
- 방화벽과 공개 포트 정책 적용
- 서버 애플리케이션 디렉터리 확정

완료 조건:

- `chronyc tracking`이 동기화 상태
- 업데이트 후 SSH 접속 정상
- 외부 공개 포트는 승인된 포트만 존재

### P02 컨테이너 실행 기반

작업:

- Docker Engine과 Compose 설치
- 프로젝트 네트워크와 볼륨 정의
- 로그 크기 제한
- 컨테이너 재시작 정책
- 상태 점검과 자원 제한

완료 조건:

- VM 재부팅 후 필수 컨테이너 자동 시작
- 로그 무제한 증가 방지
- 내부 서비스 포트가 외부에 노출되지 않음

### P03 로컬 Ollama 벤치마크

진행 시점: P04~P10의 비AI 시스템 기반 완료 후 재개.

작업:

- 시험용 Ollama와 `ornith:9b` 준비
- 짧은/중간/긴 PostgreSQL 항목 테스트
- JSON 강제, thinking 비활성화 테스트
- 처리시간, 토큰속도, 메모리, CPU 기록
- 연속 처리 안정성 시험

완료 조건:

- 6.2의 채택 기준 결과가 작업 기록에 수치로 남음
- 채택/제한/탈락 결론과 사유가 기록됨

### P04 애플리케이션 골격

작업:

- Django와 PostgreSQL 구성
- 수집용 Django 관리 명령과 systemd timer 구성
- 관리자 인증과 권한
- DB 마이그레이션
- 상태 점검 URL

완료 조건:

- 로그인과 권한 분리 정상
- DB 장애를 상태 점검에서 감지
- 재배포 후 데이터 유지

### P05 공식 문서 수집기

작업:

- 릴리스 인덱스 수집
- 원문 스냅샷과 해시
- 릴리스 노트 계층 파싱
- 중복 방지와 변경 감지
- 실패 항목 격리

완료 조건:

- 재수집 시 중복 없음
- 모든 항목에 공식 URL과 원문 존재
- 파싱 실패가 별도 오류로 노출됨
- 원문 변경 시 이전 스냅샷 유지

### P06 버전 비교 엔진

작업:

- PostgreSQL 10 이전/이후 버전 규칙
- 시작 패치 이후와 목표 패치까지 범위 계산
- 메이저 기능과 마이너 수정 분리
- 지원상태와 EOL 표시
- 변경 관계 후보 관리

완료 조건:

- `9.2.10 → 18.4` 포함 범위 검증
- 역방향과 잘못된 버전 차단
- 베타/RC 기본 제외

### P07 AI 및 OmniRoute

진행 시점: P04~P10의 비AI 시스템 기반 완료 후 진행.

작업:

- 모든 경로 실패 시 작업이 실패 상태로 보존
- 잘못된 JSON이 승인 데이터로 저장되지 않음

작업:

작업:

- 알려진 한계가 보고서에 표시됨
- 출시 체크리스트 완료

## 9. Git 작업 방식

1. 로컬 작업 폴더가 소스 기준이다.
2. 기능별 작은 커밋을 사용한다.
3. 커밋 전 테스트와 변경 요약을 확인한다.
4. 사용자에게 알린 뒤 `main`에 push한다.
5. VM 배포는 Git 기준 커밋을 사용한다.
6. VM에서 직접 수정하지 않는다. 긴급 수정도 로컬에 역반영한다.

권장 커밋 형식:

```text
docs: add project plan and work log
infra: add compose runtime
feat: collect PostgreSQL release notes
test: cover pre-10 version ordering
fix: preserve failed parser items
```

## 10. 현재 알려진 위험

| 위험 | 대응 |
|---|---|
| VM NTP 미동기화 | P01에서 최우선 해결 |

| 무료 API 정책과 한도 변경 | 활성화 시 재확인, 예산 차단, 다중 경로 |
| OmniRoute 변경 또는 장애 | 버전 고정, 직접 공급자 모드 유지 |
| 공식 HTML 구조 변경 | 원문 보관, 파서 테스트, 실패 격리 |
| AI 사실 생성 | 근거 ID, JSON 검증, 사람 승인 |
| 100GB 디스크 | 모델 수 제한, 로그 회전, 70% 경고 |
| 단일 VM 장애 | 외부 백업과 복구 시험 |
